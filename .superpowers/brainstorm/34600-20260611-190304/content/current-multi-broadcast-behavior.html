Current behavior: same-day multiple broadcasts / restarts

How zzk handles a streamer who goes live twice on the same calendar day, or restarts the stream after a crash/tech issue.

Scenario A — Two separate lives (different titles)

Timeline (2026-06-11)
10:00 — Live ON “아침 방송”
11:30 — Live ENDED (Chzzk status ENDED)
11:45 — Live ON “점심 방송” (new live_id / new title)
13:20 — Live ENDED
What gets written today
recordings/
└── 모카형/
    2026-06-11/
    ├── 아침_방송.m3u8 + chunk/ (segments...)
    └── 점심_방송.m3u8 + chunk/ (segments...)

DB: two rows in recordings (both status=completed, different started_at)

Scenario B — Same title, stream restart (tech problem)

Timeline
20:00 — Live ON “저녁 방송”
20:47 — Stream crashes / user restarts OBS → Chzzk sees brief OFF then new OPEN (new live session)
20:48 — Monitor detects live again → starts second recorder
Resulting files (current code)
recordings/모카형/2026-06-11/
├── 저녁_방송.m3u8 + chunk/ (first 47 min)
└── 저녁_방송_204802.m3u8 + chunk/ (new session from 20:48)

Two separate DB recordings. No link between them.

Current rules in code

  • Every start_recording_for_channel creates a brand new ChzzkRecorder and a new DB row.
  • prepare_paths + _make_unique_playlist_name only guarantees filename uniqueness by appending _HHMMSS or _N when the sanitized title already exists in that date folder.
  • Segments always land in a flat chunk/ next to their own .m3u8. No cross-recording continuation.
  • Monitor will happily start a second recording for the same channel if it sees is_live and the channel_id is not currently in the active dict.
  • Playback is always per-.m3u8; there is no “master of the day” playlist that stitches multiple sessions.

Pain points often reported:

What works

  • Crash-safe per session (each .m3u8 + its chunks is independently playable)
  • Clear separation: different lives = different files

Problems

  • Viewer has to open two players to watch “one evening”
  • UI shows N separate “recordings” for what felt like one broadcast
  • No automatic “continuation” when the same live title re-appears minutes later
  • Hard to answer “what did I record on 2026-06-11 for this channel?” as a single thing
A

Same-day splits are usually fine

I’m okay with multiple files per day. Just make sure the naming is clear and the UI groups them nicely.

B

Prefer automatic merge/continuation

If the streamer restarts within N minutes and the title is “similar”, continue appending to the previous recording’s playlist instead of creating a second file.

C

User-controlled (stop + “append” or “new” choice)

When we detect a possible restart of the same broadcast, ask or offer a button: “Continue previous recording” vs “Start fresh recording”.

D

Always split, but make the grouping obvious

Keep separate files, but add a “session group” or “broadcast day” concept so the UI and file browser show “2026-06-11 저녁 방송 (2 parts)”.
